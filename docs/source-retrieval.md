# Abduzeedo, Fast Company и GameSpot

Проверка 16 ноября 2026 года. Доступность CMS из GitHub Actions ещё не проверена. Ниже — результаты из среды разработки, без изменения production-БД и вызовов моделей.

## Результаты

| Источник | Проверка | Результат |
|---|---|---|
| Abduzeedo | 5 последних страниц, действующий парсер | HTTP 200, текст 1905–6590 символов, галереи 7–11 кадров с обложкой |
| Abduzeedo CMS | 10 последних статей на `cms.abduzeedo.com` | 10/10 HTTP 200, текст 1910–6590 символов, 6–10 фотографий тела |
| Fast Company | 5 последних страниц | 5/5 HTTP 403 |
| Fast Company RSS | 20 элементов | Полный текст у всех, минимум 3215 символов до нормализации пробелов |
| GameSpot | 5 последних страниц | 5/5 HTTP 403 |
| GameSpot RSS | 15 элементов | 14 полных статей; оставшийся элемент — видео, уже исключаемое правилом `/videos/` |

У Abduzeedo проверены путь без завершающего слеша, `www`, короткий браузерный User-Agent, `rss-parser`, страница CMS, RSS CMS и индекс JSON:API. Все ответили HTTP 200 локально. Это не доказывает, что смена User-Agent исправит отказ на IP GitHub. Основной сайт использует Astro; публичная CMS — Drupal с телом в `article .field--name-body` и относительными изображениями `/sites/default/files/...`.

## Реализованное поведение

- Fast Company и GameSpot: `feedDescriptionIsFull` разрешает использовать `description` как полный HTML. Удаляются скрипты, стили, iframe и служебные контейнеры. Далее применяется существующая очистка и ограничение 12 000 символов. При наличии хотя бы 600 символов запрос страницы пропускается. Это эвристика достаточности: если издатель начнёт отдавать длинные анонсы, настройку придётся пересмотреть.
- Если RSS короткий или пустой, остаётся попытка страницы. Раньше полный текст попадал в запасное поле `rawSummary`: HTTP 403 не означал потерю всей статьи. Теперь RSS становится явным основным контекстом. Галереи этих двух источников уже собирались из RSS и продолжают собираться оттуда.
- Abduzeedo: основной канал — `https://cms.abduzeedo.com/rss.xml` (`primaryFeedUrl`). При ошибке сети/HTTP, повреждённом XML, пустом фиде или отсутствии пригодных статей с телом — резерв `https://abduzeedo.com/rss.xml`. Максимум две сетевые попытки CMS и одна резервного фида; каждый запрос ограничен 15 секундами. На следующем запуске CMS снова первая. В исправном режиме публичный RSS и страницы статей не запрашиваются.
- Тело, обложка и галерея берутся из полей Drupal внутри RSS. Заголовок, автор и дата вне тела исключаются. Ссылки CMS приводятся к `https://abduzeedo.com/{slug}/` до проверки известных статей и записи coverage. Старый `rssUrl` сохраняется как идентификатор источника в БД: миграция и новая строка `sources` не нужны.
- Обычный RSS остаётся коротким: для его статей используется страница основного сайта, затем при отказе одна попытка страницы CMS. Таймаут страницы CMS — 15 секунд, лимит чтения — 1,5 МБ, повторов нет.
- HTTP 200 без тела CMS не считается успехом. При двойном отказе ошибка содержит обе причины и проходит существующий учёт `pageErrors`. Успешное восстановление пишет `резервный источник abduzeedo-cms` со ссылкой в лог; `pageErrors` не увеличивается.
- Парсер CMS ограничен телом статьи, исключает автора, теги и соседние материалы вне тела. Относительные изображения разрешаются от хоста CMS. Обложка при отсутствии метатега берётся существующим механизмом из RSS.

Диагностика содержит `fetchedUrl` и при переходе на резерв `primaryFeedError`. Если оба фида отказали, обычный `feedError` содержит обе причины. Успешный резерв не считается полным отказом источника; причина переключения остаётся в JSON-диагностике и текстовом логе.

Реальная резервная ветка страницы проверена с имитацией 403 основного сайта и настоящим запросом CMS: 2552 символа и 7 фотографий. Две фотографии проверены HEAD: HTTP 200, `image/jpeg`. Автотесты покрывают также переключение RSS при отказе/пустом или повреждённом ответе, лимиты запросов и узнавание существующей публичной ссылки. Полный набор: 66 тестов; TypeScript проходит.

CMS RSS отдаёт только 10 последних статей, обычный RSS — 50. Это ограничивает догрузку после длительного простоя или при большом числе публикаций между сборами. При исправной CMS резерв не опрашивается, даже в ручной догрузке. Отсутствие новых публикаций само по себе не включает резерв: замерший, но структурно исправный фид нельзя надёжно отличить от редакционной паузы без дополнительного сравнения источников.

Основной канал проверен реальным вызовом `fetchSourceFeed`: выполнен один запрос CMS. У всех 10 элементов получены текст, обложка и галерея; нормализованные ссылки и даты публикации совпали с обычным RSS. Для этого сравнения публичный RSS запрашивался отдельно диагностическим скриптом, а не сборщиком.

## Другие варианты

1. **Расширение окна CMS RSS.** Перед догрузкой старых публикаций стоит отдельно исследовать пагинацию или API. Автоматическое объединение двух фидов сейчас не включено: публичный RSS используется только при отказе CMS.
2. **JSON:API CMS.** Индекс доступен; сущности и пагинация не проверены. Полезен при нестабильном HTML, сейчас добавляет лишнюю интеграцию.
3. **Отдельный сборщик вне GitHub.** Резервный вариант, если CMS тоже блокирует Actions. Потребует хостинга, мониторинга и безопасного обмена данными. Сначала нужно проверить CMS на runner.
4. **Браузерный рендеринг.** Пока избыточен: текст есть в серверном HTML или RSS. Дороже обычного запроса и сам по себе не решает блокировку адресов GitHub.

После выкладки нужно проверить новую статью Abduzeedo: `fetchedUrl` в диагностике, сохранённый контекст и галерею. Уже сохранённые короткие статьи автоматически не пересобираются — известные ссылки пропускаются.
